# Rumi recovery console: verified context

## Repository and runtime

This repository contains frontend/, backend/, demo/, integration/, context/ and plan/.
Rumi/ is a submodule of https://github.com/cjleemesotes/Rumi pinned to
`0070811dde8e960c46aabaef052a3aef9f136078`, the existing recovery-API merge.
The original development checkout also has an unrelated optional-agent-ID edit;
the console always supplies an explicit ID and does not need or publish that edit.

One Python HTTP server serves both API and frontend at http://127.0.0.1:8765/.
Worker children run on the same machine with the same Python executable. No live
model or external payment service is involved. The SQLite write and process exit are real.
See README.md for first-clone setup and the single startup command.

CODE_ROOT is derived from package locations. STORAGE_ROOT defaults to CODE_ROOT;
isolated checks supply temporary storage and another loopback port. Each UUID run
has `.rumi-console/runs/<run_id>/run.json`, `ledger.sqlite3` and a `rumi/` tablet directory.
The active run is selected by `.rumi-console/active.json`. Runtime data is not committed.

## Existing dependency APIs

- `agent.pending_tool_calls()` returns a list: empty, or one supported unfinished call
  with request_idea_id, tool_call_id, tool_name and decoded arguments. Unsupported
  history raises UnsupportedRecoveryError with diagnostic reason/calls.
- `agent.record_recovered_result(request_idea_id, tool_call_id, result)` saves a
  caller-confirmed outcome without rerunning the tool or model. An equal repeated
  outcome returns the same result idea without writing. A different result conflicts.
- `agent.whirl()` raises RecoveryNeededError before saving input or contacting the
  model when an unfinished call is present.
- Instances cache history per World. Inspect/recover uses a fresh World/process;
  stale history must not be repaired by appending around it.

Library sources: Rumi/src/rumi/agent/recovery.py and agent.py. Existing real-crash
fixture/tests: Rumi/tests/recovery_agent.py and tests/test_recovery.py.
Read RUMI_GUIDE.md for the public API constraints and source map.

## Real demo flow and identity

`demo.cashier.Cashier` remains defined in demo/cashier.py in every process. The agent
ID is till-1, tool is record_payment and deterministic call ID is call_pay_1. The
original request idea ID is generated by Rumi and retained in run.json before recovery.

The parent creates the fixture table, then starts a crash child. A deterministic
mock model request asks for order A-1, amount 42. The actual tool inserts, commits
and closes the database, then calls os._exit(17) before returning. Fresh inspection
therefore finds one row, zero saved results and one pending call.

Recovery validates the stored request and reads every ledger row through a read-only
SQLite URI. Exactly one strictly matching row is required. Missing, duplicate,
mismatched or unreadable evidence stays unresolved. The recover child records the
confirmed row values through Rumi; a different fresh inspection must then find one
literal recovered result, one ledger row, zero pending calls and the same result idea ID.
No tool/model continuation occurs. Repeat recovery, refresh and restart preserve that result.

## Architecture and shared contracts

- frontend/ renders backend evidence as text, preserves the original request,
  distinguishes unknown evidence, and never automatically retries a POST.
- backend/ owns HTTP validation, routing, static allow-list and exclusive loopback binding.
- demo/runtime/ owns pure shared policy, storage and child orchestration without importing
  Rumi/Cashier. demo/workers/ opens agents and performs inspection/recovery in children.
- demo/runtime/contract.py centralizes identity, paths, strict validators, timing and
  the error catalogue. Public facades remain at demo.runner and backend.server.
- integration/ owns startup/import checks and isolated complete-flow verification.
  Expectations stay independent of application constants. Preservation checks capture
  Rumi's starting revision, status and file/diff fingerprints, then compare after the run.

SPEC.md defines endpoints, complete State examples, refusal behavior and completion criteria.
Root/folder CLAUDE.md files and READMEs provide the current editing guide.

## Verification history and publication

The development tree passed 304 complete-flow checks, including the actual crash,
independent inspection, recovery, repetition, refresh, restart, run isolation,
unsupported history, invalid requests and focused refusal cases. The dependency's
25 focused recovery tests also passed; its preparation full-suite baseline was 205.
Publication verifies the same flow against a clean pinned checkout rather than relying
on the original machine's uncommitted-file fingerprint.

The implementation used five existing owner sessions; no duplicate implementation
sessions were needed. A later three-task read-only Haiku evaluation passed 3/3 with
a 23/24 headline score. Published summaries and prompts are in evaluations/haiku/.
It was a comprehension/planning evaluation, not an implementation benchmark.

Local terminal/process records, raw model traces, generated databases and machine
verification artifacts remain in the prepared workspace and are excluded from Git.
The public repository contains the application, specification, plan, guides and reviewed summaries.
